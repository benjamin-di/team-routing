# Reset-aware routing (1.8.1)

The objective is to use included quota before it expires. Ownership only breaks exactly equal scores. Configured owned Claude identities are exempt from default shared-account reserves unless explicitly customized; ownership grants no numerical bonus and has no 70% weekly switch.

## Eligibility and hard reserves

The native host filters disabled accounts, requested-model support and cooldowns. Preflight verifies cached quota but does not treat an account-wide last-error flag as a cooldown for every model; the host checks actual model-specific cooldowns at selection. Request-free evaluation reports that distinction. Claude/Codex require recent quota; all Claude accounts require a weekly sample no older than polling interval plus 60 seconds; the five-hour window is applied only when the provider reports one. Exhausted or projected-exhausted included quota is blocked. Extra/credit usage never supplies eligibility.

With `require_extra_usage_disabled: true` (new-install default; optional for best-effort deployments), every Claude subscription, including owned accounts, also needs an explicit provider `extra_usage.is_enabled: false` from a reading no older than polling interval plus 60 seconds. Enabled/unknown/stale billing settings are blocked even with full included quota. Explicit fast/priority and credit-fallback requests are rejected before inference. Actual reported overage use creates a persistent account fence that automatically recovers only after fresh usable included quota is confirmed in a newer window. Provider-side billing must remain disabled; account owners changing it externally between samples and previously incurred spending are outside a quota scheduler's control. In strict mode, Team accounts whose billing cannot be disabled with available permissions remain excluded from native inference as well.

With `require_extra_usage_disabled: false`, enabled or unknown provider credit settings no longer exclude healthy subscription quota. Recent complete included quota remains required (polling interval plus 60 seconds). Explicit paid requests and persistent observed-paid-use fences remain enforced regardless of this flag. When provider credits are enabled or unknown, one estimated next-request buffer is also preserved in each included window, including owned accounts and unlocked weekly tails. Shared reserves, projected active usage and cache affinity remain in force. This is best-effort protection: quota lag, external usage and concurrent requests can still cause provider-side paid spillover. It cannot guarantee zero credit charges.

Paid-use blocks recover automatically when a fresh complete quota reading is newer than the latest paid response and proves a new five-hour or weekly window (with 90-second jitter tolerance). For an idle full five-hour allowance with no active reset timestamp, quota monitoring remembers the last actual reset boundary. A fresh reading beyond that boundary plus the tolerance can recover; only when no boundary is known does recovery wait five hours plus tolerance from the last paid signal. The same included-quota ranker must confirm usable allowance above all reserves and request buffers; strict billing mode additionally requires provider credits OFF. Fresh readings in the same window, timer expiry alone, stale or missing quota, and still-protected/exhausted allowance cannot clear a block. Recovery is persisted before eligibility resumes, requires no proxy restart, and is recorded in bounded private `team-routing-credit-events.jsonl`. A new paid response immediately reblocks the account and updates the latest signal time, including in-flight responses. File errors fail closed. This prevents an old billing signal from excluding renewed usable subscription quota indefinitely; it does not eliminate provider-side paid spillover.

Claude admission also retains estimated completed-request reservations until a newer quota reading covers them, with a 15-second settlement allowance. Active requests remain separately reserved; usage and terminal callbacks deduplicate by shared selection/account identity, with request identity as a fallback. These reservations and response quota constraints persist in `team-routing-admission.json` across restarts. Successful response headers provide a monotone per-window limit from five-hour and weekly utilization/reset values, allowing a one-percentage-point rounding margin. They can reduce cached availability, never raise it within the same window; old/higher out-of-order responses cannot reopen an account. The actual response reset is used for whole-session protection even if an older poll lacks it. Newer lower response readings reconcile estimates preceding that observation (retaining settlement work), preventing many tiny cache-hit requests from falsely exhausting a budget between polls. A protected five-hour window also keeps a minimum two-percentage-point next-request uncertainty buffer; protected weekly windows keep half a point, or a larger existing rate/request buffer.

These are admission constraints on new proxy requests, not a provider-side guarantee: already-running requests, variable request cost, delayed provider counters, and external account use can cross a reserve. New private decision fields record reported/projected five-hour allowance, actual reset, reserve, quota age, completed debt and the response constraint; usage records retain only parsed numeric quota feedback. No raw headers, prompts or tokens are added. Config-backed credentials with known quota receive the same preflight generic 429 even when absent from the auth-file list.

For shared Claude accounts:

- Preserve 15% weekly remaining until its scheduled unlock. With `weekly_release_mode: reset_schedule` and a five-hour final window, a weekly reset during Sunday–Thursday, 11:00–20:00 PKT unlocks five hours before reset. Every other reset unlocks at the preceding 20:00 PKT: same day for resets from 20:01 onward, previous day for morning resets and Friday/Saturday daytime resets. 20:00 is included in the daytime minute; 20:01 begins night. Unknown/passed resets cannot release the reserve. Owned accounts are exempt. An omitted mode keeps the legacy fixed-hours rule for portable installs.
- Preserve 20% five-hour remaining for the whole session overlapping Sunday–Thursday, 11:00–20:00 in system time (Asia/Karachi in the scheduling example), including portions outside those hours. Session start is inferred as reset minus five hours; a new session is planned prospectively. The optional timezone override is unchanged.

Forecasts and a next-request buffer are applied before either floor. Affinity, ownership and any expiry priority cannot bypass them. Provider sampling, variable request size, external account use and already-running requests prevent an absolute provider-side percentage guarantee.

## Weekly planning

1. Convert remaining weekly quota to equivalent full five-hour allowances. `weekly_five_hour_ratio` defaults to the user's approximate 5× estimate. Reliable paired changes learn a separate ratio per account/group/weekly window. Samples must stay within unchanged reset windows (90-second timestamp jitter tolerance), show at least five percentage points of five-hour use and one point of weekly use, and imply a ratio between 1 and 30. Existing estimates are smoothed and survive idle samples/resets; they remain estimates, not token prices.
2. Count usable capacity in remaining five-hour opportunities until weekly reset. The current window contributes its projected usable headroom, constrained by weekly quota and demand before that window's own reset. Future windows follow five-hour cycles and respect protected-hour reserves. Available time and observed eligible demand constrain a partial last opportunity. Planning is bounded to the next seven days. When demand is unknown, assume one five-hour allowance per hour solely for planning; actual provider limits still apply.
3. Divide remaining weekly equivalents by those opportunities. If the 15% weekly reserve is still locked, also plan to consume the currently spendable equivalents before the reserve unlocks. Use the higher pressure. The same scheduled unlock instant drives both the eligibility floor and pre-unlock pacing, so ranking cannot release the reserve early or keep targeting an obsolete 24-hour deadline.
4. Higher pressure gets higher ordinary priority. Its score uses the smooth bounded value `2 × pressure / (1 + pressure)`, with small adjustments for immediately spendable headroom, active work and sample age. There is no 85% avoidance rule or old reset-grace exception. Legacy cutoff/expiry fields are accepted but ignored and removed on dashboard save.

For example, 64% weekly remaining at the initial 5x conversion represents 3.2 five-hour equivalents. A Sunday 18:00 PKT reset releases the final 15% at Sunday 13:00. Until then, pacing plans spendable 49% against opportunities before 13:00, and all 64% against opportunities before 18:00. Whole-session five-hour reserves still apply. Learned conversion and observed demand can change ranking.

## Five-hour expiry and affinity

Parallel selections first prefer accounts with the fewest active or pending requests, after all eligibility and reserve checks. Deadline ranking chooses within that pool. An existing binding yields if its account is busier; it otherwise keeps the existing warmth and urgency thresholds. This avoids assigning an entire subagent burst to one high-scoring account while other eligible accounts are idle. It imposes neither a hard concurrency cap nor a request queue, and cannot guarantee provider throughput. Already-running work is untouched. Native retry and cooldown enforcement remain authoritative.

A current five-hour window gets an immediate-expiry tier only when its reset is within an hour and at least five percentage points of usable capacity are predicted to expire unused at the observed eligible demand rate. Protected capacity is excluded. This real waste opportunity can temporarily override ordinary weekly planning; strong observed demand that can consume it removes the override. No active window is invented for this override when the provider reports no reset.

Conversations keep their binding when urgency is similar. Without recent measured caching, the switch threshold is the larger of 0.02 and 20% of the held score (score floor 0.05). Successful native cache reads/writes increase this smoothly, weighted by the cached fraction of input, to at most 0.04 and 35%. Warmth lasts conservatively five minutes from request start; it is evidence of recent caching, not proof a provider entry still exists. Missing/failed token records cannot establish warmth. Body-only and native session identities are isolated by caller and provider/model; subagents can have distinct bindings. Prompts/cache controls are preserved.

Hard eligibility and imminent five-hour expiry bypass affinity. An earlier weekly planning deadline within 24 hours also bypasses it when raw weekly pressure is greater than 1 and exceeds the held pressure by both 50% and 0.25. This avoids score saturation hiding a threatened weekly budget. There is no ten-minute minimum binding duration. Already-running requests are never interrupted. Exact-score ownership ties do not dislodge healthy affinity.

As of 1.7.1, conversation identity is the host's `canonical_session_id` after native session enrichment. The host handles protocol headers, body IDs, subagents and inferred sessions. Team Routing hashes that identity with caller/provider/model scope and keeps only quota-aware account retention. It no longer parses those identities independently or transports them in a private request header. A missing native identity falls back to caller/provider/model scope. Existing in-memory bindings warm again after the upgrade; prompts, cache controls and provider-side caches are unchanged.

As of 1.8, failed usage records without positive token measurements and known client/auth/validation/rate-limit terminal rejections do not create estimated completed-request debits. Measured partial work remains reserved even if it fails, and canceled/unknown/timeout/conflict outcomes remain conservative. This prevents retry failures from artificially consuming subscription quota. Antigravity `5h` aliases normalize to the existing five-hour path, including cached rate keys, so they no longer receive generic daily-normalized short-deadline scores. Existing explicit native-window rules using the old alias remain effective; if multiple aliases describe one window, the highest currently active floor wins deterministically.

## Diagnostics and reliability

Before inference, the plugin checks enabled accounts advertising the exact effective model against the same cached quota eligibility rules. If none qualifies, version 1.3 returns generic HTTP 429 `rate_limit_error` with "Usage rate limited. Please try again later." and `Retry-After` (normally 30 seconds, up to 300 seconds for exhausted pools, shortened near a known reset). Internal account/reserve/reset details go only to private diagnostics. This reads only native inventory and cached quota. Unknown/incomplete model inventory defers to native routing, which still enforces eligibility at selection. This improves exhausted-pool reporting; it cannot replenish quota or guarantee the absence of every native routing error.

The dashboard exposes weekly equivalents, spendable equivalents, opportunities, planning deadline, conversion source, expiry risk and score for eligible accounts. Version 1.3 adds actual selection candidate scores/eligibility and switch reasons, hashed session correlation, measured provider cache tokens, affinity retention and switch counts. Raw token shares are not subscription billing weights. Missing usage is not a cache miss. These per-account diagnostics are indicative; actual scheduling also filters for the requested model/provider and considers bindings. Native terminal outcome attribution remains distinct from independently verified client success.

The shared quota cache, provider backoff, reset wakeups, pending-selection reservations, stateless Claude thread negotiation and bounded sanitized event log remain enabled. Quota-read HTTP 429 responses retry after 30 seconds initially, doubling on consecutive failures up to two hours; a longer provider `Retry-After` or Antigravity `google.rpc.RetryInfo` delay always takes precedence. The worker honors due times for accounts visited in its current scan without adding a minimum sleep to overdue retries. Backoff never renews the cached observation timestamp or relaxes admission freshness, so prolonged monitoring failures still block stale quota and billing data. Ordinary provider prompt caching is retained through full-history requests and similar-urgency account affinity. No official CLIProxyAPI source or management UI changes are required. This is a transparent online heuristic; future demand, provider rounding and unknown conversion ratios prevent a claim of global optimality.


## Authoritative policy and dashboard contract

GET /v0/management/plugins/team-routing/schema publishes the plugin version, JSON Schema (draft 2020-12), field definitions, groups and read-only engine parameters. Runtime validation and dashboard field bounds consume the same registry in policy_spec.go. Time-zone, weekday uniqueness, hour ordering and freshness relationships are validated semantically. Unknown settings are rejected. Legacy cutoff fields remain read-compatible only and disappear on the next dashboard save.

GET .../state returns the saved policy/revision, evaluated rules, discovered client keys, actual provider/model catalog, global account eligibility and diagnostics. The overview is model-independent; POST .../evaluate and actual admission check model-specific limits. An exhausted Sonnet or Cowork limit cannot block unrelated Opus; the OAuth-app-wide window remains applicable. Disabled credentials, missing enabled models and native cooldowns are visible. Evaluation performs no inference or forced provider refresh.

PUT .../policy validates provider/model pairs against the runtime registry and uses optimistic concurrency for policy and active-key changes. All exposed settings, including diagnostics and strict billing mode, persist when explicitly submitted. New requests read saved policy directly. POST .../refresh checks only due readings, respecting cache coalescing and backoff. Separate embedded CSS/JavaScript resources use a restrictive content security policy. Engine constants are read-only, versioned and returned by the schema. Estimates are heuristics, not subscription prices.


## Per-account percentages (1.6)

`account_reserves` maps native credential IDs to complete five-hour/weekly percentage pairs. After the provider protection switch, explicit per-account values take precedence over defaults and the owned-default exemption. Without a custom rule, shared accounts use provider default floors and owned accounts remain exempt. Version 1.7 supports normalized quota from Claude, Codex and Antigravity; only reported applicable windows participate.

All reserve calculations use the same effective settings resolver: immediate admission, weekly release/floor and pacing, future five-hour opportunities, paid-fence recovery and dashboard diagnostics. An override changes percentages only; schedule, freshness, uncertainty buffers, exhaustion checks and credit safety remain in force. Zero is explicit, not inheritance. Removing the account entry restores defaults/exemption. Rules persist across token refreshes and disconnects, but a different native credential ID does not inherit another rule.

## Client model rules and provider policies (1.7)

`model_routes[client_hash][exact_requested_id]` contains either `{ "action": "requested" }` or `{ "action": "override", "provider": "advertised-provider", "model": "advertised-model" }`. Resolve once against the original requested model: an exact rule wins, otherwise `routes[client_hash]` supplies the default override, otherwise preserve the request. A pass-through exception also overrides a default redirect. No fuzzy matching, target chaining or automatic fallback across model generations occurs. Rules may use unadvertised source aliases; override targets must be advertised pairs.

`account_ownership[id]` explicitly sets ownership for any provider. Absent an entry, legacy email ownership still applies only to Claude. Ownership only breaks equal ranking scores and exempts provider default reserves; explicit reserves and credit safeguards still apply. `provider_reserves[provider]` uses the same validated schedule fields as Claude, whose existing `shared_claude` field is retained. New providers start without enabled reserve policies. Each provider switch controls its defaults and account-specific rules.

`window_reserves[id][native_window_key]` specifies the reported group/window identity, remaining floor and optional release within 0–10080 minutes of a confirmed future reset. Daily/hourly/model-specific windows keep their native identity; credit balances cannot become subscription allowance. Without a five-hour window, ranking compares spendable fraction per remaining day across reported deadlines, with the existing active-work, freshness and affinity constraints. It does not invent five-hour cycles or a weekly conversion. All-providers ownership and routing remain available when no normalized quota adapter exists; those providers retain native availability and cooldowns without percentage promises.
